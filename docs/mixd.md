# 音声エンジン（mixd）

P2 レーンA の骨格。設計書の「device-io」「mixer-core」「control-server」に当たる部分と、録画用の共有メモリ書き出しを持つ。エフェクト・VST3（A1）、プロセス音声（A3）、LAN（N）、録音・サンプラーは P3 以降。

## 構成

| ファイル（apps/mixd/src） | 役割 | スレッド |
|---|---|---|
| `controller` | パラメーターツリーの変更を受けてミックス計画とデバイス要求を作り直す。デバイス一覧・入力状態・負荷・音切れ回数の公開、メーター送信、トラックの追加・削除・移動 | 制御（asio） |
| `plan_builder` | ツリーと開いているポートから `MixPlan`（処理順、ルーティング、ソロ、キュー、共有メモリのスロット）を作る純粋関数 | 制御 |
| `engine` | 計画をブロック境界で差し替え、入力ポートから読み、ミキサーを回し、出力デバイスと共有メモリへ書く | 音声（クロック） |
| `mixer` / `dsp` | チャンネルストリップ（Lo-Hi フィルター、フェーダー、パン、センド、キュー）とメーター | 音声 |
| `device_manager` | 要求されたデバイスのストリームを開閉し、クロック基準を選び、切断・失敗から復帰する | デバイス |
| `wasapi_backend` | WASAPI のエンドポイント一覧・変更通知・ストリーム（共有／排他） | 各ストリーム |
| `fake_backend` | テスト用の仮想デバイス（Linux でもエンジン全体を動かせる） | 各ストリーム |

JUCE はデバイス入出力には使わない。JUCE の WASAPI は入力1台と出力1台を1本のスレッドで組にし、エンドポイント ID も公開しないので、「トラックごとに別の入力デバイス」に合わない。JUCE は P3 のエフェクトと VST3 ホストで使う。

## 音の流れ

```
入力デバイス ─(ストリーム)→ ClockBridge ─┐
                                          ├→ エンジン（クロック基準の出力デバイスのコールバック）
入力デバイス ─(ストリーム)→ ClockBridge ─┘     │
                                                ├→ クロック基準の出力デバイス（直接）
                                                ├→ ClockBridge → 他の出力デバイス
                                                └→ 共有メモリ（capd へ）
```

- エンジンは1台の出力デバイスのクロックで動く。その他の入出力は V2 で合格した `ClockBridge`（QPC で測る PI 制御＋可変レート sinc）でつなぐ。
- クロック基準：`/system/clock_device` → マスターの出力先（1〜8 の順）→ 使われている他の出力 → どれも使えなければ内部タイマー。外れたら次の候補へ自動で切り替え、戻れば元に戻す。今の基準は `/system/clock_active`。
- ブリッジの目標遅延は「(デバイス周期＋エンジン周期)×2＋2ms」。`mixd --bridge-ms` で下限を上げられる（仮想デバイスや USB で音切れするとき）。

## チャンネルストリップ

入力（デバイス＋他トラックからの出力）→ ローカット → ハイカット →［pre：録画・キュー・プリフェーダーセンド］→ フェーダー → パン →［post：出力先・センド・録画］

- フィルターは 2 次バターワース。オン・オフは 10ms のクロスフェード、周波数の変更は滑らかに追従する。
- フェーダー・パン・センド・ミュートは 5ms で滑らかに変化（クリックノイズ防止）。新しいトラックは無音からフェードイン。
- パン：モノトラックは定パワー（中央 −3dB）、ステレオトラックとマスターはバランス。
- ソロ：ソロのトラックと、それに流れ込むトラック・それが流れ込むトラックだけが鳴る。
- キュー：`cue` のトラックのフェーダー前（PFL）を `/cue/target` へ `/cue/volume_db` で送る。
- メーターはフェーダー後・パン前。
- 共有メモリ：`/capture/audio/#/source` のトラックとマスターを書く。`record/tap` が pre ならトラックのチャンネル数、post ならステレオ。

## 共有と排他

`/system/audio_mode`：

- shared：48kHz float で開き、Windows がデバイスのミックス形式に変換する（44.1kHz のデバイスもそのまま使える）。周期はデバイスの既定（通常 10ms）で、`/system/block_size` はエンジン内部の処理単位になる。
- exclusive：48kHz で開ける PCM 形式（float32 / int32 / int24 / int16）を探し、周期を `/system/block_size` に合わせる（デバイスの最小周期が下限）。48kHz に対応しないデバイスや、他のアプリが排他で使っているデバイスは開けず、`device.error` イベントで理由を知らせる。

## 録画の開始・停止

docs/spec/protocol.md 5.4.1 のとおり。エンジンは状態（`/capture/state` など）を持ち、実際の録画は capd（role = サービス、名前 `capd`）が行う。`/capture/record/start` で `starting`、capd の `/capture/report state=recording` で `recording`（`elapsed_ms` はエンジンが 250ms ごとに更新）、`stop` で `stopping`、`report idle` で `idle`。録画中に capd が切断すると `error`。

## 試験

- `ctest`：`[mixd]` のテストがフィルター、パン、ミキサー（ルーティング、センド、キュー、ミュート）、共有メモリ、計画（ソロ、入力状態、デバイス要求）、仮想デバイスでのクロック切り替え、制御サーバー越しの結合を確かめる。
- `mixd --fake-devices`：音声ハードウェアなしで UI などから接続できる。
- G2「バッファ128〜256で音切れなし」：`scripts\g2-engine.ps1`。1kHz のテストトーンをマスターに流し、共有モードはループバックの正弦波フィットで音切れを数え、両モードで `/system/xruns`（デバイスの欠落、周期の取りこぼし、ブリッジのアンダーラン）と `/system/cpu_load` を記録する。
