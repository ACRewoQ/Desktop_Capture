# 音声エンジン（mixd）

P2 レーンA の骨格と P3 レーン A2（入出力の拡張）。設計書の「device-io」「mixer-core」「control-server」に当たる部分と、録画用の共有メモリ書き出しを持つ。LAN（送信ストリーム・LAN 入力・ペアリング・相手 PC）は P3 レーン N で追加。P3 レーン A3 で「recorder」（トラック別録音）と「sampler」を、レーン A1 で内蔵エフェクトと VST3 ホストを足した。

## 構成

| ファイル（apps/mixd/src） | 役割 | スレッド |
|---|---|---|
| `controller` | パラメーターツリーの変更を受けてミックス計画とデバイス要求を作り直す。デバイス一覧・入力状態・負荷・音切れ回数の公開、メーター送信、トラックの追加・削除・移動 | 制御（asio） |
| `plan_builder` | ツリーと開いているポートから `MixPlan`（処理順、ルーティング、ソロ、キュー、共有メモリのスロット）を作る純粋関数 | 制御 |
| `engine` | 計画をブロック境界で差し替え、入力ポートから読み、ミキサーを回し、出力デバイスと共有メモリへ書く | 音声（クロック） |
| `mixer` / `dsp` | チャンネルストリップ（Lo-Hi フィルター、フェーダー、パン、センド、キュー）とメーター | 音声 |
| `device_manager` | 要求されたデバイスのストリームを開閉し、クロック基準を選び、切断・失敗から復帰する | デバイス |
| `wasapi_backend` | WASAPI のエンドポイント一覧・変更通知・ストリーム（共有／排他）、プロセス音声（process loopback）と音声を出しているアプリの一覧 | 各ストリーム |
| `asio_backend` | ASIO ドライバー（1 つだけ開く。全チャンネルを 1 つのコールバックで入出力） | ドライバー用 STA スレッド、ドライバーのコールバック |
| `fake_backend` | テスト用の仮想デバイス（Linux でもエンジン全体を動かせる） | 各ストリーム |
| `fx_manager` | エフェクトスロットの追加・削除・移動、パラメーターの受け渡し、VST3 の読み込みとスキャン、プラグイン一覧の公開 | 制御 |
| `fx/builtin` | 内蔵エフェクト 6 種（eq4・comp・gate・reverb・delay・limiter）と `FxSlot`（バイパスのクロスフェード） | 音声 |
| `vst3/vst3_host`（apps/mixd/vst3） | JUCE 9 による VST3 ホスト（スキャン用の子プロセス、キャッシュ、プラグインの画面） | JUCE のメッセージ（メイン） |
| `lan_service` | LAN 側：`lan/<n>` に送られたバスを購読者へ送る（ポート `lan:<n>`）、入力の種類 `lan` のトラックへ相手の送信ストリームを流す（ポート `lan:<相手>/<n>`、クロックズレ補正つき）、`/lan/subscribe`、ペアリング、`/lan/peers/#` | 制御、UDP 受信、送出（1 ms） |
| `lan_peer_link` | ペアリング済みの相手 PC ごとの制御接続（role = peer）。相手の `/lan/stream/#` を写し、こちらのトラックが使うストリームを購読する | 相手ごと |
| `lan_store` / `discovery` | サーバー ID・ペアリング・トークンの保存（`%APPDATA%\DesktopCapture\mixd-lan.txt`）、mDNS（`_dcmix._tcp`） | 制御 |
| `recorder` | トラック別録音のテイク：ファイルごとのロックフリー FIFO と書き込みスレッド | 音声（書き込み）、ディスク |
| `audio_file` | 24bit WAV / FLAC の書き出し、WAV / FLAC / MP3 / Ogg Vorbis の読み込みと 48kHz への変換 | ディスク、読み込み |
| `sampler` | パッドの発音（ボイス、モード、バンクごとのバス）と読み込みスレッド | 音声、読み込み |
| `control_bindings` | ホットキーと MIDI の割り当て（`/control/*`）：状態の検査、ホットキーの登録、MIDI 入力の一覧と開閉、動作の実行、学習、保存（`%APPDATA%\DesktopCapture\mixd-control.txt`） | 制御 |
| `control_input_win` / `control_input_fake` | エンジンの PC のキーボード（`RegisterHotKey`、学習中だけ低レベルキーボードフック）と MIDI 入力（winmm）。テスト用の偽物 | ホットキー用スレッド、MIDI ドライバー |

JUCE はデバイス入出力には使わない。JUCE の WASAPI は入力1台と出力1台を1本のスレッドで組にし、エンドポイント ID も公開しないので、「トラックごとに別の入力デバイス」に合わない。JUCE は VST3 ホストだけに使う（内蔵エフェクトは自前）。

## 音の流れ

```
入力デバイス ─(ストリーム)→ ClockBridge ─┐
                                          ├→ エンジン（クロック基準の出力デバイスのコールバック）
入力デバイス ─(ストリーム)→ ClockBridge ─┘     │
                                                ├→ クロック基準の出力デバイス（直接）
                                                ├→ ClockBridge → 他の出力デバイス
                                                └→ 共有メモリ（capd へ）
```

- エンジンは1台の出力デバイスのクロックで動く。その他の入出力は V2 で合格した `ClockBridge`（QPC で測る PI 制御＋可変レート sinc）でつなぐ。
- クロック基準：`/system/clock_device` → マスターの出力先（1〜8 の順）→ 使われている他の出力 → どれも使えなければ内部タイマー。外れたら次の候補へ自動で切り替え、戻れば元に戻す。今の基準は `/system/clock_active`。
- ブリッジの目標遅延は「(デバイス周期＋エンジン周期)×2＋2ms」。`mixd --bridge-ms` で下限を上げられる（仮想デバイスや USB で音切れするとき）。

## 48kHz 以外のデバイス（自前のレート変換）

エンジンは 48kHz 固定。44.1kHz・96kHz などで動いているデバイスは、ストリームの中で `clocksync::RateConverter`（固定比の sinc 補間、64 タップ、下げるときは出力側のナイキストの 90% で切る）で 48kHz と相互に変換し、残るクロックのずれは今までどおり ClockBridge が吸収する。

- shared：ミックス形式のレートのまま開く（Windows の変換は使わない。G2 で UR22 の 44.1kHz に数分に 1 回の欠落が出たため）。開けないときだけ P2 と同じく 48kHz で開いて Windows に変換させる。
- exclusive：48kHz、デバイス形式のレート、ミックス形式のレート、44.1k、96k、88.2k の順に排他で使える PCM 形式を探す。どれもなければそのデバイスだけ共有で開く。
- ASIO：ドライバーが 48kHz にできればそうし、できなければドライバーのレートで変換する。
- 変換しているデバイスはログに `device note: <名前>: 44100Hz で動いているため 48kHz と相互に変換している` を出す。`/devices/*/#/sample_rate` でも分かる。

## プロセス音声

`/track/#/input/kind = process`、`source` = 実行ファイル名（protocol.md 4.4）。

- 同じアプリを指すトラックが何本あっても取り込みは 1 本（ポートのキーは `process:<小文字の実行ファイル名>`）。Windows 10 は 1 プロセス内で同じ PID を 2 回開けないため（V1）。
- 実行ファイル名のプロセスツリーの根（親が同じ名前でないもの）を子プロセスごと取り込む。根が複数なら音声セッションのある方、次に古い方。
- アプリが終了すると（プロセスハンドルで検知）ストリームが失敗扱いになり閉じ、トラックは `disconnected`。デバイスマネージャーは 3 秒ごとに同じ名前を探し、起動していればつなぎ直す。
- `/devices/process/#` は 5 秒ごと（と `/devices/refresh`）に、全出力デバイスの音声セッションから作る。

## ASIO

`HKLM\SOFTWARE\ASIO` のドライバーを、入力 1 台（`asio:<名前>`、全入力チャンネル）と出力のステレオ組（`asio:<名前>:1-2` …）として一覧に出す。チャンネル数は最初の一覧のときにドライバーを一度読み込んで調べる（失敗したものは 10 秒後に再挑戦）。`mixd --no-asio` で使わない。

- 同時に開けるドライバーは 1 つ（2 つ目は `device.error`）。開いたら全入出力チャンネルのバッファを作り、各ストリームはコールバックの中で自分のチャンネルだけを読み書きする。使っていない出力は無音。
- バッファサイズは `/system/block_size` をドライバーが受け付ければそれ、だめならドライバーの設定画面の値。
- ASIO の出力がクロック基準なら、エンジンは ASIO のコールバックで動く。ASIO の入力も同じコールバックで ClockBridge に入る。
- ドライバーがリセットやレート変更を求めたら（`kAsioResetRequest` など）全 ASIO ストリームを閉じて開き直す。
- ドライバーの宣言（IASIO と構造体）は SDK を入れずに `asio_backend.cpp` に書いてある（ASIO SDK 2.3 と同じ配置）。

## 切断・復帰と ID の再照合

設計書「デバイス切断時の動作（音声）」の表のとおり。P2 のクロック切り替えと再オープンに加えて：

- 設定で使っているデバイス・アプリが消えたら `device.lost`、戻ったら `device.restored`（`id`, `name`, `kind`）。起動時から無いものは「消えた」とは言わない。
- サンプルレートの変更や USB の差し替えで Windows がデバイスに新しい ID を付けたら、エンジンが名前で照合して設定（入力元・出力先・センド・キュー・クロック基準）を新しい ID に書き換え、`device.rematched` を送る。同じ向き・同じ名前の接続中デバイスがちょうど 1 台で、まだどこからも使われていないときだけ。同じ名前がなければ、別の USB ポートで Windows が付ける番号を除いて比べる（`Line (2- Steinberg UR22)` = `Line (Steinberg UR22)`。実機試験で、挿し直した UR22 がこの名前・44.1kHz で登録し直された）。名前は起動してから見たデバイスの分だけ覚えている。
- VB-CABLE などの仮想ケーブルへのブリッジは目標遅延を 50ms 以上にする（V2：仮想デバイスは数十 ms 止まることがある）。

## チャンネルストリップ

入力（デバイス＋他トラックからの出力）→ ローカット → ハイカット → エフェクト（スロット順）→［pre：録画・キュー・プリフェーダーセンド］→ フェーダー → パン →［post：出力先・センド・録画］

- フィルターは 2 次バターワース。オン・オフは 10ms のクロスフェード、周波数の変更は滑らかに追従する。
- フェーダー・パン・センド・ミュートは 5ms で滑らかに変化（クリックノイズ防止）。新しいトラックは無音からフェードイン。
- パン：モノトラックは定パワー（中央 −3dB）、ステレオトラックとマスターはバランス。
- ソロ：ソロのトラックと、それに流れ込むトラック・それが流れ込むトラックだけが鳴る。
- キュー：`cue` のトラックのフェーダー前（PFL）を `/cue/target` へ `/cue/volume_db` で送る。
- メーターはフェーダー後・パン前。
- 共有メモリ：`/capture/audio/#/source` のトラックとマスターを書く。`record/tap` が pre ならトラックのチャンネル数、post ならステレオ。

## エフェクトと VST3

スキーマと手順は docs/spec/protocol.md 5.7・5.8、パラメーターの一覧は protocol-params.md。

- スロットはフィルターの後、pre の前。`/track/#/fx/add`（`/master/fx/add`）で足し、`remove`・`move` で番号が詰め直される（トラックと違って固定 ID ではない）。
- パラメーターとバイパスはアトミック値で音声スレッドへ渡す（計画の作り直しなし）。内蔵エフェクトの値は 32 サンプルごとに滑らかに追従、バイパスは 10ms のクロスフェード。
- プラグインの遅延補正はしない（`latency_samples` で知らせるだけ）。リミッターは 1ms（48 サンプル）の先読みがある。
- VST3：パラメーターのキーは `p<ParamID>`、値は 0〜1。ツリーに載るのは最初の 128 個と、`params` で読んだもの・プラグインの画面で動かしたもの（1 インスタンス最大 1024）。画面で動かした値は 20ms ごとにまとめて公開する。
- 読み込みは非同期で、`status` が `loading` → `ok` / `failed`。キャッシュにないプラグインは `missing`。
- スキャン：`/plugins/scan` で、プラグインのファイルごとに子プロセス（`mixd --scan-plugin FILE --out JSON`）を起動し、落ちたり 60 秒で終わらないものは `crashed` / `timeout` として一覧に残す。結果は `%APPDATA%\DesktopCapture\vst3-cache.json`（`--plugin-cache` で変更）に保存し、次回の起動ではスキャンしない。探す場所は標準の VST3 フォルダーと `/plugins/extra_dirs`。
- スレッド：VST3 があるとき、メインスレッドは JUCE のメッセージループ（プラグインの生成と画面）を回し、エンジンは別スレッドで動く。`--no-plugins` で VST3 ホストなし。
- Windows では JUCE を既定でビルドする（`DC_WITH_JUCE`、Linux は既定 OFF）。

## トラック別録音（recorder）

docs/spec/protocol.md 5.4.2 のとおり。エンジンが自分でファイルに書く（capd は関係しない）。

- 開始時に、録音対象（`record/enabled`）・タップ・チャンネル数を決めて `RecorderTake` を作る。テイクはミックス計画に載り、音声スレッドが毎ブロック、対象の各トラックをファイルごとの FIFO（4 秒分）に入れる。全ファイルが同じブロックから始まり、同じ長さで終わる。
- 書き込みスレッドが FIFO を 20ms ごとに空にしてファイルへ書く。FIFO があふれたブロックは捨てて数え、書き込みスレッドが同じ長さの無音を足す（位置は FIFO の量の分だけずれうるが、長さは保つ）。
- 停止はテイクのない計画を作り、エンジンが採用するのを待ってから（最大 0.5 秒）ファイルを閉じる。
- 録音中に削除されたトラックは無音で続ける。モノ⇔ステレオを変えたときは開始時のチャンネル数に合わせて変換する。
- WAV は 5 秒ごとにヘッダーを書き直す（落ちても途中まで開ける）。4GB を超えると RF64（JUNK チャンクを ds64 に置き換え）。FLAC は libFLAC（圧縮レベル 5）。
- `/recorder/with_capture` が true なら、`/capture/state` が `recording` になったときに始め、`recording` でなくなったら止める（手で始めた録音は録画に関係なく続く）。

## サンプラー

docs/spec/protocol.md 5.4.3 のとおり。

- `file` が変わると読み込みスレッドがファイル全体を読み、48kHz ステレオの float にする（モノは両チャンネルへ、3 チャンネル以上は先頭 2 つ、48kHz 以外は窓付き sinc で変換。ダウンサンプルではカットオフを下げる）。デコーダーは third_party/audio_decoders の dr_wav・dr_flac・dr_mp3・stb_vorbis。
- 読み込んだ音は `SamplerTable`（128 パッドの音・モード・音量）としてミックス計画に載る。押す・離す・止めるはロックフリーのキューで音声スレッドへ届く。
- ボイスは 32。停止・頭出し・音の差し替えは 5ms のフェード。足りなければ一番古いボイスを使う。再生中にファイルを差し替えると、その音は新しい計画の採用時に止まる（古い計画と音が解放される前）。
- 各バンクがステレオのバスに鳴り、`input/kind = sampler` のトラックが全バンクの和か 1 バンクを入力に足す（トラックのフィルター・録音・キューの前）。
- `playing` はメーターと同じ約 30Hz で、変わったパッドだけ配る。

## ホットキーと MIDI

docs/spec/protocol.md 5.9 のとおり（P4 C7）。

- 割り当てが変わるたびと、トラック・映像ミックス・エフェクトが増減するたびに全部の割り当てを検査し直し、`state`・`error` を書く。同じキーの組み合わせは 1 回だけ登録し、全部の割り当てに配る。
- ホットキーはメッセージ専用ウィンドウを持つ専用スレッドで `RegisterHotKey`。押されたら 15ms ごとに `GetAsyncKeyState` を見て離したことを知る（パッドの「押す間」用）。`step` の割り当てがあるキーだけ自動の繰り返しを受ける。他のアプリが持っている組み合わせは `conflict` で、3 秒ごとに登録し直してみる。
- 学習中だけ `WH_KEYBOARD_LL` のフックを入れ、修飾キー以外のキーが押された瞬間の修飾の状態で組み合わせを決める。そのキーの押下と離しは他のアプリに渡さない。
- MIDI 入力は 3 秒ごと（と `/devices/refresh`）に一覧を取り直し、`enabled` の機器を開く。他のアプリが開いていると `busy`（`MMSYSERR_ALLOCATED`）で、次の見直しで開き直す。消えた機器は閉じる。
- ボタンとして使う CC とノートは、押した・離したの変わり目だけで動く（127 を 2 回送るパッドでも 1 回）。`param` の値は割り当てごとに約 60Hz に間引き、最初の値はすぐ反映する。
- 動作はクライアント名 `control` の Set / Call として、クライアントと同じ検査を通す（`ControlServer::applyLocalSet`・`callLocal`）。
- `mixd --control-store FILE` で保存ファイルを変える。`--no-hotkeys` はホットキーも MIDI も使わない（割り当ては `unsupported`。本物のエンジンと並べて試験するとき）。

## 共有と排他

`/system/audio_mode`：

- shared：ミックス形式のレートの float で開く（48kHz 以外はエンジンが変換）。周期はデバイスの既定（通常 10ms）で、`/system/block_size` はエンジン内部の処理単位になる。
- exclusive：PCM 形式（float32 / int32 / int24 / int16）を 48kHz から順に探し（上の「48kHz 以外のデバイス」）、周期を `/system/block_size` に合わせる（デバイスの最小周期が下限）。排他で使える形式がないデバイスはそのデバイスだけ共有モードで開き、ログに `device note` を出す。他のアプリが排他で使っているデバイスは開けず、`device.error` イベントで理由を知らせる。

排他モードで頼んだ周期どおりに動かないデバイスもある（Steinberg UR22 のドライバーは 128/256 を受け付けるが 10ms ごとにしか起こさない）。各ストリームは最初の 1 秒で起こされる間隔と入力のデータ欠落を測り、合わなければ実際の周期（デバイスの既定周期に近ければその値）で開き直す。それでも駄目なら共有で開く。どちらもログに `device note` を出す。

機器の注意（G2 で分かったこと）：

- 44.1kHz で動いているデバイスを共有モードで使うと、Windows の変換で数分に 1 回データ欠落（DATA_DISCONTINUITY）が出ることがあった（UR22、P2）。P3 からは Windows に変換させず自前で変換する。ドライバー側（UR22 は Yamaha Steinberg USB Driver）と Windows のサウンド設定の「既定の形式」は同じレートにそろえる。レートを変えると Windows はデバイスを別 ID で登録し直す（エンジンが名前で照合し直す）。
- 共有モードの入力は 100ms のバッファで開く（遅延は増えない）。10ms では読み遅れでなくても欠落が出た。
- デバイスの位置（GetBuffer の devicePosition）は、共有モードで変換されるデバイスではデバイス側のレートで数える。

## LAN

制御プロトコルの 8 章（検出・ペアリング）と 10 章（購読）、docs/spec/lan-media.md。

- 既定で 0.0.0.0:47800 で待ち受ける。同じ PC からの接続はそのまま、LAN からはペアリング済み（トークン）か、ペアリング受付中に正しい 6 桁コードを出した「リモコン」と「相手 PC のエンジン」だけを受ける。`--local-only` で従来どおり 127.0.0.1 だけ（LAN 機能なし）、`--allow-remote` はペアリングなしで受ける（開発用）。
- UDP 47810（`--media-port`）で LAN 音声を送受信。`--no-discovery` で mDNS を使わない（相手は `/lan/peers/add` でアドレス指定）、`--lan-store` で保存ファイルを変える。
- 相手 PC のストリームを使う手順：`/lan/peers/#` に相手が見えたら（または `/lan/peers/add`）、相手で `/remote/pairing/start`、こちらで `/lan/peers/pair id=<相手> code=<6桁>`。あとはトラックを `input/kind = lan`、`input/source = <相手の id>/<n>` にすると、相手が `lan/<n>` に送っている音が届く（`input/state` = ok、`input/lan_delay_ms` に受信バッファの量）。

## 録画の開始・停止

docs/spec/protocol.md 5.4.1 のとおり。エンジンは状態（`/capture/state` など）を持ち、実際の録画は capd（role = サービス、名前 `capd`）が行う。`/capture/record/start` で `starting`、capd の `/capture/report state=recording` で `recording`（`elapsed_ms` はエンジンが 250ms ごとに更新）、`stop` で `stopping`、`report idle` で `idle`。録画中に capd が切断すると `error`。

## 試験

- `ctest`：`[mixd]` のテストがフィルター、パン、ミキサー（ルーティング、センド、キュー、ミュート）、共有メモリ、計画（ソロ、入力状態、デバイス要求）、仮想デバイスでのクロック切り替え、制御サーバー越しの結合を確かめる。
- `[fx]` のテストが内蔵エフェクトの音（EQ の利き、コンプの圧縮量、ゲート、リバーブ・ディレイの尾、リミッターの天井）、バイパス、偽のプラグインホストでのスロット操作を確かめる。`dc_vst3_tests`（JUCE ありのとき）がテスト用プラグイン DC Test Gain でスキャン・キャッシュ・読み込み・パラメーター・音声処理と、落ちるプラグインのスキャンを確かめる。
- `[mixd][a2]`（tests/test_mixd_io.cpp）：仮想アプリのプロセス音声（1 本で 2 トラック、終了で disconnected・再起動で復帰）、ID の再照合、切断・復帰イベント。`[clocksync]` の rate converter：44.1k⇄48k の歪みと折り返し。
- `mixd --fake-devices`：音声ハードウェアなしで UI などから接続できる。
- G2 結合（UI 操作中の音切れ・録画の音ズレ）：`scripts\g2-integration.ps1`。`mixd --test-pulse 2` はテストトーンを QPC 時刻の 2 秒ごとの 50ms のビープにする（共有メモリに書くブロックの時刻で揃えるので、`dc-av-flash` の画面フラッシュと録画の中で比べられる）。
- `[lan]` のテスト：mixd 2 台を 1 プロセスで動かし、片方のマスターを `lan/1` に送り、もう片方のトラックで鳴らす（レベルが届く、購読の出入り、相手 PC の追加・ペアリング・削除、peer の制限）。ループバック以外のアドレスがあれば、リモコンと相手 PC のペアリング（コード違い、トークン、取り消し）も確かめる。
- A2 の実機試験：`scripts\a2-io.ps1 -Cases list,process,rate,asio,vmic,unplug`（詳細はスクリプト冒頭）。
- `[recorder]` `[sampler]` のテスト（tests/test_recorder_sampler.cpp）：WAV / FLAC の往復、リサンプラー、パッドのモード、テイクの長さ、制御サーバー越しの録音とサンプラー。
- A3 の実機確認：`scripts\a3-check.ps1`（`-Minutes`、`-Formats`、`-InputDevice`）。テストトーン入りのマスターと、サンプラー・入力のトラックをフェーダーを動かしながら録音し、全ファイルの長さ・欠落・xrun・トーンの途切れを調べる。続けて Windows の効果音 16 個をパッドに読み込み、各モードの動きを確かめる。
- `[control]` のテスト（tests/test_control.cpp）：きっかけの読み書き、キー名、MIDI の解読、割り当ての検査、MIDI の値の当てはめ、偽のキーボード・MIDI での実行・conflict・学習・機器の開閉・保存と読み込み。
- C7 の実機確認：`scripts\c7-control.ps1`（`-Midi` で MIDI 機器の学習も）。SendInput でキーを押して、ホットキー・自動の繰り返し・conflict・学習・無効・再起動後の復元を確かめる。
- G2「バッファ128〜256で音切れなし」：`scripts\g2-engine.ps1`（`-Device` で出力、`-WithInput -InputDevice` で入力を選ぶ）。xrun のログ行には時刻、ストリームごとの実測レート、ブリッジの比率、入力欠落の様子が出る。1kHz のテストトーンをマスターに流し、共有モードはループバックの正弦波フィットで音切れを数え、両モードで `/system/xruns`（デバイスの欠落、周期の取りこぼし、ブリッジのアンダーラン）と `/system/cpu_load` を記録する。
