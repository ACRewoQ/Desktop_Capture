# V1 技術検証：アプリ単位の音声キャプチャー（Process Loopback）

開発計画フェーズ 1 の V1「Win10 / Win11 実機でアプリ単位の音声を取れるか」の結果です。

## 結論

- **合格（Win11・Win10 とも）**：WASAPI の Process Loopback で、指定したアプリ（とその子プロセス）の音だけを取れました。ほかのアプリの音は 30dB 以上、実測ではノイズフロア以下まで落ちています。
- **Win10 22H2（build 19045）でも動きました。** SDK の資料は「build 20348 以降」としていますが、19045 の実機で全項目が動作しました。計画の「ダメだった場合：Win10 はデバイス単位ループバックのみ」は**不要**です。ただし Win10 の古いビルド（21H2 以前）は試していません。動かない環境ではデバイス単位ループバックに切り替える作りは残します。
- **Win10 だけの制約が 1 つ**：1 つのプロセスの中で、同じ PID を 2 回キャプチャーすると 2 回目が `IAudioClient::Initialize` で `0x8000FFFF (E_UNEXPECTED)` になります。違う PID なら 7 本同時でも問題なく、別プロセスからなら同じ PID も開けます。Win11 では同じ PID を 31 本同時に開けました。
- **設計への反映**：エンジン（mixd）は**1 つの PID（プロセスツリー）につきキャプチャーを 1 本だけ開き、それを複数のトラックへ配る**。同じアプリを 2 トラックにアサインしても Win10 で動きます。

## 計測方法

`dc-loopback-probe selftest` が自動で次を行います（テスト音 -20dBFS が約 2.5 秒鳴ります）。

1. 自分自身を子プロセスとして 3 つ起動し、既定の出力にサイン波を鳴らさせる：A = 1000Hz、B = 1500Hz、ツリー = 700Hz（子プロセスがさらに孫プロセスを起動し、孫が鳴らす）
2. 次の 35 本のキャプチャーを同時に開く（48kHz float ステレオ、イベント駆動、20ms バッファ）
   - A の include、B の include、ツリーの親の include（孫の音が入るか）、A の exclude、既定デバイスのループバック
   - 追加で A の include を 30 本（同時に多数開けるか）
3. 開始イベントで子プロセスに一斉に鳴らさせ、終了後 1.5 秒ほどキャプチャーを続ける（対象プロセスが終了しても止まらないか）
4. 各キャプチャーの 700 / 1000 / 1500Hz の振幅を 2 秒窓の Goertzel で測る。窓を長くしているのは、同時に鳴っている他のアプリの音（声や音楽）を誤ってテスト音と数えないためです

`dc-loopback-probe multi --pids a,b,c` は 1 つのプロセス内で複数のキャプチャーを開き、それぞれの結果を表示します（Win10 の制約の切り分けに使用）。

## 結果

### 分離（振幅、テスト音は 0.100）

| キャプチャー | 700Hz | 1000Hz | 1500Hz | Win11 | Win10 |
|---|---|---|---|---|---|
| A include | 0.000 | **0.100** | 0.000 | 合格 | 合格 |
| B include | 0.000 | 0.000 | **0.100** | 合格 | 合格 |
| ツリー include（孫が鳴らす） | **0.100** | 0.000 | 0.000 | 合格 | 合格 |
| A exclude | **0.100** | 0.000 | **0.100** | 合格 | 合格 |
| デバイス ループバック | **0.100** | **0.100** | **0.100** | 合格 | 合格 |

数値は両 OS で同じでした（小数第 3 位まで）。

### 測定値

| 項目 | Win11 | Win10 |
|---|---|---|
| アクティベーション時間 | 平均 0.4ms、最大 7.6ms（35 本） | 平均 5.0ms、最大 17.0ms（5 本） |
| 同時に開けた本数（同じ PID、1 プロセス内） | 31 本（include 30 本 + 最初の 1 本） | 1 本（2 本目から E_UNEXPECTED） |
| 同時に開けた本数（違う PID、1 プロセス内） | 3 本（試した分すべて） | 7 本（試した分すべて） |
| CPU（このプロセス、キャプチャー同時稼働中） | 1 コアの 6.2%（35 本） | 1 コアの 2.1%（5 本） |
| 遅延（テスト音を出力に渡してからキャプチャーに現れるまで） | 49.8ms | 52.3ms |
| 遅延（デバイス ループバック、参考） | 56.3ms | 37.6ms |
| パケット | 10ms ごと。無音でも届き続ける（フレーム数は経過時間の 98〜100%） | 同じ |
| パケット間の最大の隙間 | 10〜58ms | 11〜25ms |
| 対象プロセス終了後 | エラーなし、無音が届き続ける（1.6 秒分） | 同じ |
| 鳴る前の区間 | 完全な無音（-180dBFS） | 同じ |
| 形式 | float32 48kHz（AUTOCONVERTPCM、PCM16 への切り替えは不要だった） | 同じ |

遅延は「子プロセスが最初の音入りバッファを渡した時刻」と「キャプチャーのそのサンプルの QPC 時刻」の差で、出力側のバッファ（20ms）を含む概算です。

## レーン A（A2 プロセス音声）への申し送り

- 1 つの PID（ツリー）につきキャプチャーは 1 本。複数のトラックが同じアプリを使うときはエンジン内で配る（Win10 の制約）。
- アプリを指定するときは**ツリーの根の PID** を使う（ブラウザーのタブなど子プロセスの音もまとめて入る）。`list` は音声セッションの PID とツリーの根を表示します。
- 無音でもパケットは 10ms ごとに届きますが、隙間が最大 58ms あったので、トラックの入力は時計に合わせて足りない分を無音で埋める（V2 のクロック補正と同じ扱い）。
- 対象アプリが終了してもキャプチャーは止まらず無音を返すだけです。再起動したアプリは PID が変わるので、プロセス名で再アサインする仕組みが要ります（設計書の「切断時は無音、復帰で自動復旧」に合わせる）。
- exclude モード（指定アプリ以外の全部）も使えるので、「自分自身（ミキサー）の出力を除いたデスクトップ音」がアプリ単位キャプチャーで作れます。
- Process Loopback のクライアントは `GetMixFormat` などが使えないため、形式はこちらで指定し `AUTOCONVERTPCM` に変換させる。

## 試していないこと

- Win10 21H2 以前のビルド（手元にない）。
- 既定の出力デバイスを途中で切り替えたときの動作。
- 長時間（1 時間以上）の連続キャプチャー。V2 のクロック補正の検証と合わせて P2 で確認します。

## 再現手順

```powershell
# Win11（Visual Studio あり）
.\scripts\v1-loopback.ps1

# 実際のアプリを録ってみる
$probe = '.\build\windows\tools\loopback_probe\Release\dc-loopback-probe.exe'
& $probe list
& $probe capture --name chrome.exe --seconds 10 --wav chrome.wav
& $probe capture --pid 1234 --exclude --seconds 10
```

Visual Studio のない PC では、MinGW-w64 の g++ を PATH に入れて `tools\loopback_probe\build-mingw.cmd` を実行するとツール単体をビルドできます。
