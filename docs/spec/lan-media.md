# LAN メディア伝送 v1（音声・映像）

- 状態：音声は P2 レーン N 先行で実装、P3 レーン N で mixd に組み込み（購読・ペアリング・相手 PC の検出）。映像（7 章）は P3 で伝送部分を実装、capd からの送出は映像ミックス（B1）とエンコーダー拡張（B2）の後
- 実装：`libs/lanmedia`（`dc::lan`）、mixd の `lan_service`
- 試験：`dc-lan-sim`（ネットワーク模擬、`--video` で映像）、`dc-lan-tone`（実 UDP）、`dc_tests` の `[lanmedia]` と `[lan]`
- 相手はこのアプリだけです（VBAN などとの互換は持たせません。設計書「LAN メディア伝送」の節、決定事項 #5）。

## 1. 全体像

```
送信側 PC                                        受信側 PC
エンジンの音声スレッド                             エンジンの音声スレッド
  AudioSender::push(ブロック, 時刻)                 AudioReceiver::pull(出力, フレーム数, 時刻)
        │ ロックフリー FIFO                              ▲ 可変レートリサンプラー（クロックズレ補正）
  送信スレッド AudioSender::pump()                       │ デコード / 欠落の補間
        │ パケット化・エンコード                          │ 並べ替えスロット（ジッターバッファ）
  UdpTransport::send ── UDP ──▶ UdpTransport 受信スレッド → AudioReceiver::onPacket(データ, 到着時刻)
        ▲                                                │
        └──────── 受信レポート（約 1 秒ごと）◀───────────┘
```

- 1 プロセスにつき UDP ソケット 1 つ（既定ポート **47810**）。受け取ったデータグラムはストリーム ID で振り分けます。
- 送信側は購読者ごとにユニキャストで送ります（同じデータグラムを各宛先へ）。誰が何を購読するかは制御プロトコルで決めます（P3 で接続、下記「未決事項」）。
- 取りこぼしは再送しません。音声は補間で隠し、映像は受信レポートでキーフレームを要求します（映像は後日）。

## 2. パケット形式

すべてリトルエンディアン。1 データグラムは **1400 バイト以下**（Ethernet の MTU 1500 から IP/UDP ヘッダーと VPN・PPPoE の余裕を引いた値。IP の断片化を起こさない）。

### 2.1 共通ヘッダー（12 バイト）

| オフセット | サイズ | 内容 |
|---|---|---|
| 0 | 4 | マジック `DCN1` |
| 4 | 1 | 種類：1 = メディア、2 = 受信レポート |
| 5 | 1 | メディアの種類：1 = 音声、2 = 映像（レポートは 0） |
| 6 | 1 | フラグ（下表） |
| 7 | 1 | 予約（0） |
| 8 | 4 | ストリーム ID（送信側がストリーム開始ごとに乱数で決める。0 は使わない） |

### 2.2 メディアヘッダー（共通ヘッダーに続けて 24 バイト、計 36 バイト）

| オフセット | サイズ | 内容 |
|---|---|---|
| 12 | 4 | シーケンス番号（データグラムごとに +1、一周する） |
| 16 | 8 | 送信側の時刻（QPC をマイクロ秒にしたもの）。音声は先頭フレームを録った時刻 |
| 24 | 8 | 位置。音声は先頭フレームの通し番号（ストリーム開始から数えたフレーム数）、映像はフレーム番号 |
| 32 | 2 | 断片の番号（映像の 1 フレームを複数データグラムに分けるとき。音声は 0） |
| 34 | 2 | 断片の数（音声は 1） |

フラグ：bit0 = ストリームの最初のパケット、bit1 = キーフレーム（映像）。

### 2.3 音声ペイロード（メディアヘッダーに続けて）

| オフセット | サイズ | 内容 |
|---|---|---|
| 36 | 1 | コーデック：1 = PCM 16 ビット、2 = PCM 24 ビット、3 = Opus |
| 37 | 1 | チャンネル数（1 / 2） |
| 38 | 2 | このパケットのフレーム数（デコード後） |
| 40〜 | | PCM はインターリーブの符号付き整数、Opus はパケットそのもの |

- サンプルレートは 48 kHz 固定（エンジンと同じ）。
- 1 ストリームの中ではパケットのフレーム数は一定です。位置はいつもフレーム数の倍数ずつ進みます（受信側は位置でスロットを決めるため）。
- 既定：PCM 24 ビット・120 フレーム（2.5 ms、ステレオで 720 バイト、約 2.3 Mbps）。Opus は 480 フレーム（10 ms）、128 kbps、FEC あり。Opus のパケット長は 120 / 240 / 480 / 960 フレームから選びます。

### 2.4 受信レポート（共通ヘッダーに続けて 40 バイト、計 52 バイト）

受信側 → 送信側（パケットが来たアドレスへ）、約 1 秒ごと。カウンターはストリーム開始からの累計です。

| オフセット | サイズ | 内容 |
|---|---|---|
| 12 | 4 | 受け取ったデータグラム数 |
| 16 | 4 | 失われた数（シーケンス番号の抜け） |
| 20 | 4 | 遅れて捨てた数（再生の順番が過ぎてから届いた） |
| 24 | 4 | 補間で埋めた数 |
| 28 | 4 | 到着の揺らぎ（直近 20 秒の遅れの最大、マイクロ秒） |
| 32 | 4 | 受信側のバッファ目標（マイクロ秒） |
| 36 | 8 | 最後に受け取ったメディアパケットの送信側時刻（そのまま返す） |
| 44 | 4 | そのパケットを受け取ってからこのレポートを送るまでの時間（マイクロ秒） |
| 48 | 4 | 予約（0） |

フラグ bit0 = キーフレーム要求（映像）。送信側は「今の時刻 − 返ってきた時刻 − 保持時間」で往復時間を出します（録音からパケット化までの待ちも含みます）。

## 3. 受信側の動き

`AudioReceiver` がジッターバッファ・欠落の補間・クロックズレ補正を 1 か所で行います。

1. **到着時刻の追跡**（`ArrivalClock`）：パケットごとに「到着時刻 − データの終わりの位置 ÷ 48000」を出し、直近 2 秒の**最小値**を「最速の経路」とします。スイッチの待ち行列や Wi-Fi の再送はパケットを遅らせるだけで早めることはないので、最小値は遅延の突発に引きずられません。最速の経路より遅れた分が「遅れ」で、直近 20 秒の最大を揺らぎとして使います。
2. **バッファ量**＝最速の経路で届いているはずの位置 − いま再生している位置。
3. **目標**（自動）＝ 出力ブロックのフレーム数 ＋ パケット 1 個分 ＋ リサンプラーの先読み（32 フレーム）＋ 揺らぎ ＋ 1 ms。固定値も指定できます（`targetMs`）。
4. **クロックズレ補正**：V2 の `DriftController`（PI 制御）と `VariableResampler` をそのまま使い、バッファ量を目標に保つようにリサンプル比を動かします。2 台の PC の水晶のズレ（±数百 ppm）を吸収し、遅延は一定のままです。
5. **大きなズレはその場で直す**：目標より大きく足りないとき（揺らぎが増えたとき）は、直前の波形を逆向き→順向きに繰り返して継ぎ目なく引き延ばします。大きく余るとき（20 ms 以上）は先を捨ててフェードインします。300 ms 以上ずれたら再同期します。
6. **欠落の補間**：順番が来てもパケットがなければ、PCM は直前のパケットを逆向き・順向きに交互に繰り返しながら 10 ms で無音へフェードし、本物が戻ったら 2 ms でクロスフェードします。Opus は次のパケットが届いていれば FEC で元に戻し、なければコーデックの PLC を使い、40 ms を超えて続く欠落（送信側が止まったなど）は 10 ms で無音へフェードします（libopus の PLC は止まったストリームを 1 秒以上鳴らし続けるため）。あとから届いたものは「遅れ」として捨てます。
7. **ストリームの切り替え**：最初に来たストリームを受け取り、別のストリーム ID は「最初のパケット」フラグが付いているとき（送信側の再起動）だけ乗り換えます。同じストリームで遅れたパケットや遠すぎるパケットが 8 個続いたら（送信側のデバイスが止まって再開した場合など）再同期します。
8. **チャンネル**：モノラルのストリームはステレオ出力の両側へ、ステレオのストリームはモノラル出力では平均します。

スレッド：`onPacket()` は受信スレッド、`pull()` は音声スレッド。どちらもロックなし・メモリ確保なし（新しい形式のストリームが始まったときのデコーダー作成だけ例外）。

## 4. 試験の結果（クラウド、2026-10-23）

`dc-lan-sim --minutes 60`：送信側の音声デバイスがトーンを録り、ネットワークが遅延・揺らぎ・並べ替え・重複・損失・途絶を加え、受信側の音声デバイス（別のクロック）が再生します。録音された各フレームの時刻が分かっているので、端から端までの遅延を正確に測り、出力のクリックをトーン解析で数えます。

| シナリオ | 条件 | 遅延（最小〜最大） | 補間 | 結果 |
|---|---|---|---|---|
| wired-pcm24 | 有線、両 PC とも 10 ms デバイス、ズレ 120 ppm | 24.1〜24.5 ms | 0 | 合格、クリック 0、ズレ推定 120.03 ppm |
| wired-lowlat | 有線、両 PC とも 128 フレーム（2.7 ms）デバイス | 10.3〜10.7 ms | 0 | 合格、クリック 0 |
| wired-large-drift | 有線、PCM16、ズレ 800 ppm | 24.1〜24.5 ms | 0 | 合格、ズレ推定 800.34 ppm |
| wired-reorder | 遅延が指数分布（平均 2 ms）、重複 1 % | 35.2〜48.8 ms | 13 / 144 万 | 合格 |
| wired-outage | 0.5 秒の途絶 | 24.1〜24.6 ms | 途絶分のみ（200） | 合格、再同期なし |
| sender-pause | 送信側デバイスが 1 秒止まって再開 | 24.0〜24.5 ms | 停止分 | 合格、再同期 1 回 |
| sender-restart | 送信側がストリームを開き直す | 23.7〜24.5 ms | 0 | 合格 |
| wifi-opus | Wi-Fi 相当（1 % で 40 ms の突発、0.5 % ＋連続損失） | 57〜75 ms | 損失 3190 のうち FEC で 2466 を復元 | 合格 |
| wifi-pcm24 | 同じ Wi-Fi で PCM | 61〜72 ms | 損失分 | 合格（損失は補間音になる） |


読み取れること：

- 設計目標「LAN 音声の追加遅延 10〜20 ms」は、**両側のデバイスが 128〜256 フレーム**のとき満たします（約 10 ms）。WASAPI 共有モードの 10 ms デバイスでは、送信側が 10 ms ごとにまとめて送ること自体が約 10 ms の揺らぎになるため約 24 ms になります。
- 有線ではクリック 0・補間 0 で、遅延は 1 時間で 0.5 ms 以内しか動きません（ジッターバッファとクロックズレ補正が一緒に効いている）。
- Wi-Fi は遅延の突発に合わせてバッファが伸びるため 60 ms 台になります。Wi-Fi には Opus（FEC）を勧めます。

`dc-lan-tone loop`（実 UDP、127.0.0.1）でも、PCM24・Opus とも暖機後の損失・遅れ・補間・クリックは 0 でした。

## 5. 道具

```powershell
# 2 台の PC の間で（受信側を先に起動）
dc-lan-tone recv --seconds 120                      # 受信側。1 秒ごとに統計、最後に PASS / FAIL
dc-lan-tone send --to 192.168.1.20 --seconds 125    # 送信側。受信レポート（損失・揺らぎ・往復時間）を表示
dc-lan-tone send --to 192.168.1.20 --codec opus     # Opus で
# 1 台で（ループバック）
dc-lan-tone loop --seconds 30
# ネットワーク模擬
dc-lan-sim --minutes 10                              # 全シナリオ
dc-lan-sim --scenario wifi-opus --minutes 60
```

Windows ファイアウォールが受信側の UDP 47810 を止める場合は、初回の確認ダイアログで「プライベート ネットワーク」を許可してください。

## 6. エンジンへの組み込み（P3）

- **購読**：制御プロトコルの 10 章（`/lan/subscribe`、`/lan/sub/#`）。送信ストリームの設定は `/lan/stream/#`、受信バッファ目標は `/track/#/input/lan_buffer_ms`。映像は capd が `/lan/sub/#` に並ぶ購読者へ送る（`video/preview` は UDP 47811 から、`video/next` は UDP 47813 から、`video/lan` は UDP 47812 から。`proto::lanSubscriptions`、`docs/capd.md`「プレビューと LAN 映像の送出」）。
- **mDNS での検出とペアリング**：制御プロトコルの 8 章。mixd の `discovery`（Windows の DnsServiceRegister / Browse / Resolve）、`lan_store`（`%APPDATA%\DesktopCapture\mixd-lan.txt`）。
- **リモコンのモニター音声**（P4）：リモコンの dc-ui は `lan::AudioInput`（自分のソケット・`AudioReceiver`・受信レポート・映像と同じノック先 UDP 47810）で `audio/<n>` を購読し、端末の既定の出力で鳴らす。
- **DSCP（QoS）マーキング**：Windows では qWAVE API が要るので、必要になったら追加する。

## 7. 映像ストリーム

音声と同じ共通ヘッダー・メディアヘッダー（種類 = 映像）に、断片ごとの映像ヘッダーを続けます。1 フレーム（H.264 のアクセスユニット、Annex B、IDR の前に SPS/PPS）を 1352 バイトずつの断片に分け、各断片が 1 データグラムです。

### 7.1 映像ヘッダー（メディアヘッダーに続けて 12 バイト、計 48 バイト）

| オフセット | サイズ | 内容 |
|---|---|---|
| 36 | 1 | コーデック（1 = H.264） |
| 37 | 3 | 予約（0） |
| 40 | 4 | フレーム全体のバイト数 |
| 44 | 4 | この断片のバイトがフレームのどこに入るか |

メディアヘッダーの位置 = フレーム番号（ストリーム内で連番）、時刻 = そのフレームを撮った時刻、断片の番号と数、bit1 = キーフレーム。

### 7.2 動き

- **再送しない**。受信側は、断片が欠けたフレームを捨て、次のキーフレームまで後続も捨て（デコードできないため）、受信レポートの bit0（キーフレーム要求）で送信側に知らせます。要求はすぐ送り、キーフレームが届くまで 0.1 秒ごとに繰り返します。
- 送信側の `VideoSender::keyframeWanted()` をエンコーダーが毎フレームの前に見て、立っていれば IDR を出します。キーフレームを送って 0.05 秒以内の要求はそれで答えたものとみなします（要求が重なってキーフレームが続かないように）。
- 欠けたフレームを諦めるのは、最初の断片から「最近の到着遅れのピーク + 5 ms」（10〜150 ms）経っても揃わないとき、または後のフレームが揃ってから同じ時間が経ったときです。Wi-Fi の再送で単独のデータグラムが数十 ms 遅れても捨てずに済みます。
- 途中から見始めた受信側は最初のフレームとしてキーフレームを待ち、すぐ要求します。送信側がエンコーダーを作り直したら（`restart()`）新しいストリーム ID で 0 から数え直し、受信側はストリーム開始フラグで切り替えます。
- 実ソケットでの両端：`lan::VideoOutput`（capd：購読者への送出と受信レポート）と `lan::VideoInput`（見る側：受信・組み立て・レポート返送）。

### 7.3 試験の結果（クラウド、2026-10-24、`dc-lan-sim --video --minutes 1`）

| シナリオ | 条件 | 遅延（平均 / p99） | 最長の止まり | 結果 |
|---|---|---|---|---|
| preview-wired | 30 fps、キーフレーム 40 KB・通常 12 KB、有線 | 3.6 / 3.8 ms | 33 ms（1 フレーム） | 合格、全フレーム |
| preview-wired-loss | 同じで 0.1 % 損失 | 3.6 / 3.8 ms | 167 ms | 合格、98.9 % 表示、キーフレーム要求 17 回 |
| preview-wifi | 60 Mbit/s、揺らぎ 1 ms、0.2 % 損失・突発遅延 | 11.0 / 44.8 ms | 200 ms | 合格、96.8 % 表示 |
| preview-outage | 途絶 | 3.6 / 3.8 ms | 33 ms | 合格（途絶後キーフレーム要求 1 回で復帰） |
| preview-restart | 送信側がエンコーダーを作り直す | 3.6 / 3.8 ms | 33 ms | 合格、取りこぼし 0 |
| preview-join | 途中から見始める | 3.6 / 3.8 ms | 33 ms | 合格、最初のフレームまで 37 ms |
| lan-1080p-wired | 1080p 相当（キーフレーム 200 KB・通常 32 KB） | 3.8 / 5.1 ms | 33 ms | 合格、全フレーム |

遅延は送出から組み立て完了まで（エンコード・デコード・表示は含まない）。有線では伝送の追加遅延は 5 ms 以下です。損失があると次のキーフレームまで止まるので、止まりの長さはほぼ「往復時間 + キーフレームの送出時間」で決まります。

### 7.4 実機で試す道具

```powershell
# エンジン PC（mixd・capd 起動済み）：capd が映像ミックス（/video/preview/mix、既定 1）を送る。
# capd を使わずにテストパターンを送るときは（capd を止めてから）
dc-v6-bench --send-lan 127.0.0.1
# エンジン PC：ペアリングを始め、表示された 6 桁を見る側に入力する
dc-cli call /remote/pairing/start
# 見る側（Surface など）：初回だけ --pair、以後は保存したトークンでつながる
dc-v6-preview --engine 192.168.1.10 --pair 123456
dc-v6-preview --engine 192.168.1.10
```

見る側は空いている UDP ポートで受け、`/lan/subscribe` でエンジンに知らせます。映像の最初のパケットが届くまでは、見る側はエンジンのホストの UDP 47811（capd の送り元。`video/next` は 47813）へ中身のない受信レポート（stream_id 0、送る側は無視）を 0.5 秒ごとに送ります。返信だけを通すファイアウォール（「パブリック」ネットワークで見る側のアプリに許可がない Windows）でも映像が届くようにするためで、届いたあとは通常の受信レポートが同じ役目をします。Windows ファイアウォールの確認が出たら「プライベート ネットワーク」を許可してください（mixd の TCP 47800・UDP 47810、送る側の UDP 47811・47812・47813、見る側）。
